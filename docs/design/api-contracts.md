# API Contracts
## Cloud Log Anomaly Detection for Proactive Fault Management

Version: 1.1
Base URL: `http://localhost:8000/api/v1`
Interactive docs (generated by FastAPI): `/docs`

---

## 1. Conventions

- JSON request and response bodies; timestamps in ISO 8601 UTC with millisecond precision.
- List endpoints are paginated with `page` (default 1) and `size` (default 50, max 200).
- Time filters use `from` and `to` (ISO 8601). Default: last 1 hour.
- Errors use FastAPI's standard format: `{"detail": "message"}` with a proper HTTP status (400, 404, 422, 503).

**Paginated response envelope**
```json
{ "items": [ ... ], "total": 1240, "page": 1, "size": 50 }
```

## 2. Endpoint Summary

| Method | Path | Purpose | Data source |
|---|---|---|---|
| GET | `/health` | Health of API and its dependencies | All |
| GET | `/services` | List of monitored services | PostgreSQL |
| GET | `/logs` | Search and filter logs | Elasticsearch |
| GET | `/logs/{event_id}` | Single log event | Elasticsearch |
| GET | `/anomalies` | List anomalies | PostgreSQL |
| GET | `/anomalies/{id}` | Anomaly detail with sample logs | PostgreSQL + Elasticsearch |
| PATCH | `/anomalies/{id}/feedback` | Mark confirmed / false positive | PostgreSQL |
| GET | `/alerts` | List alerts | PostgreSQL |
| GET | `/alerts/{id}` | Alert detail with its anomalies | PostgreSQL |
| PATCH | `/alerts/{id}` | Acknowledge or resolve | PostgreSQL |
| GET | `/stats/summary` | Dashboard overview numbers | PostgreSQL |
| GET | `/stats/timeseries` | Data for trend charts | PostgreSQL |
| GET | `/models` | Model registry | PostgreSQL |
| GET | `/models/active` | Currently active model | PostgreSQL |
| WS | `/ws/live` | Real-time anomaly and alert events | Kafka `anomalies.detected` |

Dashboard statistics come from `detection_windows` in PostgreSQL, not from Elasticsearch, so the charts stay fast as log volume grows.

Alerts are created by the alerting service (Phase 8); until then the alert endpoints return empty lists, and
`alert_id` in anomalies is `null`.

## 3. Endpoint Details

### 3.1 `GET /health`
```json
{
  "status": "ok",
  "components": { "postgres": "ok", "elasticsearch": "ok", "kafka": "ok" }
}
```
`status` is `degraded` if any component is down (HTTP 503); the failing component shows `"down"`.

### 3.2 `GET /services`
Not paginated (small list).
```json
[
  { "id": 4, "name": "payment-service", "description": "Payment processing; depends on the database",
    "created_at": "2026-11-08T09:00:00.000Z" }
]
```

### 3.3 `GET /logs`
| Query param | Type | Description |
|---|---|---|
| `q` | string | Full-text search on `message` |
| `service` | string | Filter by service |
| `level` | string | Comma-separated, e.g. `ERROR,FATAL` |
| `trace_id` | string | All logs of one request |
| `from`, `to` | datetime | Time range |
| `page`, `size` | int | Pagination |

Response: paginated list of log events, newest first, in the log event schema from `contracts.md`.

Elasticsearch cannot page beyond 10,000 results this way, so `page × size` is limited to 10,000 (HTTP 400 beyond).
Narrower filters are needed for older data.

### 3.4 `GET /logs/{event_id}`
One log event in the log event schema; 404 if not found.

### 3.5 `GET /anomalies`
| Query param | Type | Description |
|---|---|---|
| `service` | string | |
| `severity` | string | Comma-separated |
| `feedback` | string | `CONFIRMED`, `FALSE_POSITIVE`, `NONE` |
| `from`, `to`, `page`, `size` | | Filter on `detected_at`; newest first |

Item:
```json
{
  "id": "c4e8a2f1-6b3d-4a9e-8c7f-0d1e2b3a4c5d",
  "service": "payment-service",
  "detected_at": "2026-11-08T10:16:02.511Z",
  "window_start": "2026-11-08T10:15:00.000Z",
  "window_end": "2026-11-08T10:16:00.000Z",
  "anomaly_score": 0.84,
  "severity": "CRITICAL",
  "model": { "id": 5, "name": "live-pca", "version": "1.1.0" },
  "summary": { "log_count": 282, "error_rate": 0.422, "avg_latency_ms": 137.4, "new_templates": 0,
               "reasons": ["error rate 42.2%"] },
  "alert_id": null,
  "feedback": null
}
```
`summary` contains all fields of the `anomalies.detected` summary (contracts.md §5.3).

### 3.6 `GET /anomalies/{id}`
Same as the list item, plus `sample_logs`: the full log events for `sample_event_ids`, fetched from Elasticsearch,
in the order of `sample_event_ids` (errors first). Logs that are no longer in Elasticsearch are omitted.
If Elasticsearch is unavailable, `sample_logs` is `[]` and `sample_logs_error` explains why (the anomaly itself
comes from PostgreSQL and is still returned).

### 3.7 `PATCH /anomalies/{id}/feedback`
Request:
```json
{ "feedback": "FALSE_POSITIVE" }
```
`feedback` is `CONFIRMED`, `FALSE_POSITIVE` or `null` (clears it). Response: the updated anomaly (3.5 item).

### 3.8 `GET /alerts`
Query params: `status`, `severity`, `service`, `from`, `to` (on `last_seen_at`), `page`, `size`.

Item:
```json
{
  "id": "e1f2a3b4-...",
  "service": "payment-service",
  "severity": "HIGH",
  "title": "High error rate in payment-service",
  "message": "error rate 42.2%",
  "status": "OPEN",
  "occurrence_count": 4,
  "first_seen_at": "2026-11-08T10:16:02.000Z",
  "last_seen_at": "2026-11-08T10:19:01.000Z",
  "acknowledged_at": null,
  "acknowledged_by": null,
  "resolved_at": null,
  "notification_sent": true
}
```

### 3.9 `GET /alerts/{id}`
The alert item plus `anomalies`: the anomaly items (3.5) grouped into this alert, newest first.

### 3.10 `PATCH /alerts/{id}`
Request:
```json
{ "status": "ACKNOWLEDGED", "acknowledged_by": "admin" }
```
Allowed transitions: `OPEN → ACKNOWLEDGED → RESOLVED`, and `OPEN → RESOLVED`. Any other transition returns 400.
Response: the updated alert item.

### 3.11 `GET /stats/summary`
Query params: `from`, `to` (on `window_start`).
```json
{
  "total_logs": 1284530,
  "total_windows": 3600,
  "total_anomalies": 42,
  "open_alerts": 3,
  "error_rate": 0.024,
  "by_severity": { "LOW": 20, "MEDIUM": 12, "HIGH": 8, "CRITICAL": 2 },
  "by_service": [
    { "service": "payment-service", "anomalies": 18, "error_rate": 0.051 }
  ]
}
```
`total_logs` and `error_rate` come from detection_windows (sum of log_count, sum of error_count / sum of log_count).

### 3.12 `GET /stats/timeseries`
| Query param | Values |
|---|---|
| `metric` | `log_count`, `error_rate`, `avg_latency_ms`, `anomaly_score`, `anomaly_count` |
| `service` | optional; all services if omitted |
| `interval` | `1m`, `5m`, `1h` |
| `from`, `to` | |

```json
{
  "metric": "error_rate",
  "interval": "5m",
  "series": [
    {
      "service": "payment-service",
      "points": [ { "t": "2026-11-08T10:00:00.000Z", "v": 0.01 }, { "t": "2026-11-08T10:05:00.000Z", "v": 0.34 } ]
    }
  ]
}
```
Aggregation per bucket: `log_count` sum; `error_rate` sum(error_count) / sum(log_count); `avg_latency_ms` mean;
`anomaly_score` max; `anomaly_count` number of anomalous windows.

### 3.13 `GET /models`
Not paginated (few models), newest first.
```json
[
  {
    "id": 5, "name": "live-pca", "version": "1.1.0", "algorithm": "pca",
    "threshold": 9.9, "training_data": "train_normal_1.jsonl, train_normal_2.jsonl, train_normal_3.jsonl",
    "training_samples": 1785, "is_active": true, "trained_at": "2026-11-13T10:30:00.000Z",
    "parameters": { "log_counts": true, "normalisation": "log_ratio" },
    "metrics": { "fault_run": { "recall": 0.952 }, "normal_run": { "false_alarm_rate": 0.0034 } }
  }
]
```

### 3.14 `GET /models/active`
The active model item; 404 if no model is active.

## 4. WebSocket — `/ws/live`

The server pushes events; the client only listens. Every message has a `type` and `data`:

| type | data | When |
|---|---|---|
| `anomaly.created` | Anomaly item (3.5) | New anomaly detected |
| `alert.created` | Alert item (3.8) | New alert opened (Phase 8) |
| `alert.updated` | Alert item | Alert grouped, acknowledged or resolved (Phase 8) |
| `ping` | `{}` | Every 30 s, keeps the connection alive |

```json
{ "type": "anomaly.created", "data": { "id": "c4e8...", "service": "payment-service", "severity": "HIGH", "anomaly_score": 0.91 } }
```

The API consumes `anomalies.detected` (group `api-group`) and converts each message from the Kafka format
(flat `model_name`, `model_version`, `model_id`) into the anomaly item format (nested `model`, plus `alert_id` and
`feedback`, both `null` for a new anomaly). The two formats differ deliberately: Kafka messages are a stable
inter-service contract, API items are shaped for the dashboard.

The dashboard reconnects automatically if the connection drops; after reconnecting it reloads recent anomalies via
`GET /anomalies`, because events sent while it was disconnected are not replayed.

## 5. Out of Scope (for now)

- Authentication: the dashboard is assumed to run on a trusted internal network. JWT login is a possible future enhancement.
- Rate limiting.
